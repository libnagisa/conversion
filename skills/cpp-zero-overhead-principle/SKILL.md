# 零开销设计

零开销有两层。**代码层**可以检验；**概念层**无法检验，只能靠深入思考，但它更重要。方案两层都过，才算零开销。

## 代码层

基准：**手写这个场景的最优实现是什么样？抽象编译出来的结果必须与它等价，不多一个字节、一条指令。**

- 没用到的功能不占字段、不占指令、不占分支
- 代价只落在真正需要该功能的路径；快路径与手写版完全一致
- 可选设施条件存在（如 `if constexpr` / 按类型特化），不无条件占位
- 复用靠编译期（模板、组合），不靠运行期统一布局（虚函数、通用 payload 槽、通用状态机）
- 判断方法：对每个新增字段/判断问"熟练的人手写这个场景，会写出它吗？"

## 概念层

- 模块只做它自己概念内的事。semaphore 就做 semaphore 的事：计数、排队、唤醒、取消排队
- **编译期信息也是开销。** 给 semaphore 加 `bool payload` 模板参数，运行时一字节不多，但引入了不属于 semaphore 的概念，增加理解负担，破坏内聚
- 不为通用而预留（payload 槽、通用状态位、"以后可能要用"的参数）
- 抽象被一次次"无害地"改写，最终模块失去内聚，是工程级灾难

可操作的检查：
- 用一句话说出这个模块是什么。新增的每个成员、模板参数、类型，能否只用这句话里的概念解释清楚？解释时要引入别的概念，就是越界
- 一个"通用"参数，对不需要它的使用者是否也成了必须理解的东西？

**需求超出原概念时，按顺序问：**
1. 是否需要一个新概念、新实体来表达它？
2. 原概念能否看作新概念的一种特例？要概念上成立，不只是代码能写成那样
3. 新旧概念各自是否内聚？
4. 依赖方向是否清晰？（比如谁依赖谁，还是两边共同依赖某个第三方内部件）

## 流程

1. **先写出手写最优版本**（可以只在草稿里），列出它的字段、快路径的指令序列。这是对照基准，之后每一步都和它比
2. **确认概念归属**：这个需求属于哪个概念？用上面的检查和四问过一遍。需要新概念就单独建，别塞进已有的
3. **先问能不能从根上不需要**，再考虑挑哪种机制：
   - 调整所有权转移时机：对象被其他线程看到之前是线程私有的，初始化在"发布"之前做完
   - 把判断合并进已有的临界区，而不是新增锁或原子变量
4. **调整顺序时不得让快路径变差**：先尝试拿资源，失败才碰慢路径设施（stop_token 注册等）。别为了消除慢路径的竞争，让最常见的路径也付代价
5. **对照手写版验证**，用下面的检验方法，不要只验证"能跑通"
6. **分清"能消除"和"只能缓解"**，结构性限制写进文档（原因、代价、调用方的解法），不用新机制掩盖

## 案例

**A. semaphore 要不要带 payload？**
反例：给等待队列加 payload 模板参数，semaphore 传空类型。运行时零成本，但 semaphore 要认识 payload，违反概念层。
做法：semaphore 保持"计数 + 队列"。带值的需求（如资源池）是另一个概念；先问它是不是新实体、semaphore 是不是它的特例、依赖方向怎样。复用的是链表算法这类最小结构接口，不是数据槽。

**B. 修"入队后才注册取消回调"导致的释放后使用**
根因：节点在还没准备好时就发布给了其他线程。把"注册取消回调"挪到"入队"之前，是从根上消除窗口，方向是对的。
但初版实现犯了两个错：
- 让"有许可直接成功"这条最常见路径也要注册、注销回调，快路径变差。应先尝试拿许可，拿不到才碰 stop_token
- 悄悄改变了语义：token 已 stop 但许可充足时，原来给许可，改后返回 stopped。修 bug 必须对照既有测试和原行为，有语义变化要明确告知，不能只写在测试注释里
此外，为仲裁新增的状态字段无条件存在，也违反代码层。应只在用到 stop callback 时存在。

**C. 同步完成链太深会爆栈**
不要断言"没有零开销解"，也不要断言"优化器会处理"或"语言保证"，两者都要用证据。用汇编或深链测试验证后再下结论。确认是结构性限制后，写进文档：原因、代价、调用方在更高层的解法。

## 检验方法

- 布局：`sizeof` / `static_assert` 对比手写版；条件存在的字段在不用时应为空
- 指令：`-O2` 看汇编，快路径与手写版对比；有需要时写基准
- 并发：TSan（竞争）、ASan/UBSan（释放后使用）下跑压力测试，包括专门撞竞争窗口的用例
- 语义：既有测试全过；边界行为（如已 stop 但有资源）逐个对照修改前后
- 概念层无法自动检验：写完回头问一遍"这个模块的一句话描述变了吗"

## 常见陷阱

- 给通用原语塞用不上的参数/类型，哪怕对不需要的场景传空类型
- 为保险加原子变量/锁，不先查能否靠调整顺序消除竞争
- 把"优化器大概率会做"当语言保证；或反过来未经验证就断言"无解"
- 在错误的抽象边界上兜底：基础设施不为防御调用方的任意行为改核心设计，限制写进文档
- 用"略增大一个字段"之类的说法淡化违反

## 汇报方式

- 先自己按本 skill 推导出结论，再汇报；汇报时说清依据（代码层等价性，或概念层归属）
- 只有推导之后仍取决于用户意图的分歧才向用户提问，并附上推荐方案和理由，不要把没想透的设计问题做成选择题
- 做了没验证的事、改了语义的事，直接说

## 自检清单

- [ ] 写过手写最优版本，每个新增字段/判断它也会有
- [ ] 不需要某功能的路径没有为它付字段、分支、锁、原子操作
- [ ] 快路径与手写版一致，慢路径设施只在慢路径使用
- [ ] 复用靠模板/编译期，不靠运行时多态或统一数据结构
- [ ] 新增成员/参数能只用模块自己的概念解释；超出的需求已过"新概念/特例/内聚/依赖方向"四问
- [ ] 既有测试和边界语义已对照，语义变化已告知
- [ ] 结构性限制已写进文档，且结论有证据（汇编/测试），不是推断
